## 1. 文档目的

本文件定义 ForgeCloud 的产品职责、系统边界、技术架构、核心数据模型、权限体系、接口规范、迁移步骤、部署方式、验证门禁和阶段交付物，用于把当前以 ForgeMind 为中心的 Spring Boot/MySQL 后端演进为 Forge 全生态共享的云平台。

ForgeCloud 不是新的三维编辑器，也不是四个产品之外的第五套业务界面。它是 ForgeMind、ForgeHub3D、ForgeLab 和 ForgeMove 共用的身份、项目、资源、协作、通知、审计和工业连接底座。各客户端继续保持独立产品体验，云端只负责跨产品必须共享和长期保存的事实。

## 2. 产品定位与生态职责

### 2.1 一句话定位

> **ForgeCloud — Industrial Intelligence Cloud**

ForgeCloud 是面向 FORGEMIND 生态的云端项目、设备、数据、模型与 AI 服务管理平台。它是统一控制面、数据面、设备面和智能服务面，统一回答“谁可以访问什么、哪个版本是正式版本、设备现在是什么状态、数据如何在产品间流动、AI 任务由什么模型执行、每次改变由谁发起并能否追溯”。

### 2.2 六层云能力

| 云能力 | 核心职责 | 关键对象 | 首要使用方 |
| --- | --- | --- | --- |
| Project Cloud | 工厂项目云端保存、版本、分支、成员协作、发布和回滚 | Workspace、Project、Version、Branch、Member、Approval | ForgeMind、ForgeLab、ForgeMove |
| Device Cloud | 设备注册、身份、在线状态、能力模型、远程控制策略和命令审计 | Device、DeviceTwin、Capability、Command、Policy、Heartbeat | ForgeMind、ForgeMove、现场系统 |
| Twin Cloud | 设备、产线和工厂数字孪生状态同步，维护模型与运行状态之间的映射 | Twin、AssetTwin、Mapping、StateSnapshot、QualityCode | ForgeMind、ForgeMove、Data Cloud |
| Asset Cloud | ForgeHub3D 模型、材质、场景、物品和资源包的云端存储、版本、许可与依赖 | Asset、AssetVersion、Model、Material、Scene、License、Dependency | ForgeHub3D、ForgeMind、ForgeLab |
| Data Cloud | 传感器、生产、质量、告警、事件和历史数据的接入、查询、保留与追溯 | DataPoint、Telemetry、ProductionEvent、Alarm、History、RetentionPolicy | Device Cloud、Twin Cloud、ForgeMove |
| AI Cloud | Agent、LLM、视觉模型和推理任务的统一路由、配额、证据、结果和审计 | Model、Provider、AgentRun、InferenceTask、Evidence、Usage | ForgeMind、ForgeHub3D、ForgeMove |

六层云能力不是六套互相割裂的产品。Project Cloud 管理业务上下文，Asset Cloud 管理被引用的模型和资源版本，Device/Twin/Data Cloud 管理现场事实，AI Cloud 只消费经过授权的项目、资产和数据并输出可审计的建议或推理结果。任何 AI 输出都不能越过 ForgeMind 的确定性碰撞、寻路、库存、物料守恒和仿真验证门禁。

### 2.3 产品职责划分

| 产品 | 主要职责 | 主要写入 ForgeCloud 的数据 | 主要从 ForgeCloud 读取的数据 |
| --- | --- | --- | --- |
| ForgeHub3D | 工业模型、物品和设备资源的创建与参数化编辑 | 资源草稿、模型文件、预览、参数 schema、版本、许可 | 企业资源库、公共资源、版本历史、依赖关系 |
| ForgeMind | 工厂设计、物流规划、确定性仿真、诊断和方案验证 | 工厂项目、正式版本、Agent 运行、审批与审计 | 资源版本、项目成员、工厂版本、运行事件摘要 |
| ForgeLab | 工厂存档、模型资源、布局和经验的开源分享 | 帖子、回复、附件、发布关系、互动和举报 | 可发布项目/资源、作者信息、许可、通知 |
| ForgeMove | 移动监控、任务、库存、异常、审批和社区入口 | 任务状态、确认、评论、通知已读、离线操作队列 | 工厂摘要、运行信号、工单、库存、社区内容 |
| ForgeCloud | 身份、组织、权限、版本、资源、事件、连接和治理 | 所有跨产品共享的长期事实 | 为四个产品提供一致 API、事件和权限判断 |

### 2.4 核心业务闭环

```text
ForgeHub3D 创建或修改资源
          ↓
ForgeCloud 保存资源草稿、版本、许可和依赖
          ↓
ForgeMind 引用固定版本进行布局、仿真和验证
          ↓
ForgeLab 发布可复现的资源包或工厂方案
          ↓
ForgeMove 接收运行摘要、任务、异常与审批
          ↓
运行反馈、使用量和问题回到 ForgeCloud
          ↓
资源与工厂方案继续迭代
```

## 3. 当前基线与差距

### 3.1 当前已有基础

当前仓库已经具备 ForgeCloud 的一部分基础能力：

- Spring Boot 3、Java 17 和 MySQL 8.4 后端。
- `app_user`、`auth_session` 用户与会话体系。
- `/api/factories` 多工厂项目存档和自动恢复存档。
- `imported_resource` 用户私有 GLB 与资源元数据存储。
- Agent run、step、tool call、event、patch 和 approval 持久化。
- ForgeLab 帖子、附件、回复、点赞和通知持久化。
- ForgeMove 对现有认证、工厂和 ForgeLab API 的移动适配。
- 工厂存档版本迁移、资源归属校验、Agent Patch 深层校验和项目行锁。

### 3.2 当前主要差距

| 领域 | 当前状态 | ForgeCloud 目标 |
| --- | --- | --- |
| 租户 | 主要按单个用户隔离 | 企业/团队工作空间，多租户强隔离 |
| 权限 | 所有者边界为主 | 工作空间角色、项目角色、细粒度权限 |
| 项目版本 | 保存完整项目和自动恢复 | 分支、提交、发布、比较、回滚、乐观并发 |
| 资源 | 用户私有导入资源 | 统一资产注册表、版本、许可、依赖、公共/私有可见性 |
| 协作 | 社区互动和 Agent 审批 | 项目成员、评论、审批、活动流和通知统一 |
| 文件 | MySQL 中保存部分二进制 | 元数据入库、对象文件进入对象存储、校验和去重 |
| 搜索 | 页面内搜索为主 | 跨项目、资源和社区的统一索引 |
| 工业数据 | 仿真与历史规划 | 只读连接器、AssetTwin、遥测、运行事件和质量码 |
| 商业治理 | 未形成 | 配额、授权、计量、企业私有库和审计导出 |

ForgeHub3D 的云端资源协议目前仍需正式定义。ForgeLab 与 ForgeMove 已有明确代码入口，但其账号、通知和资源引用仍应逐步迁入统一平台模型。

## 4. 目标与非目标

### 4.1 第一阶段目标

1. 一个账号可以加入多个工作空间，并在四个产品中共享身份和权限。
2. 工厂、模型、物品、配方和附件拥有全局稳定 ID、版本和归属。
3. ForgeHub3D 创建的资源可以在 ForgeMind 中引用并锁定版本。
4. ForgeMind 项目可以发布到 ForgeLab，并保留来源、版本和许可证。
5. ForgeMove 可以读取同一工作空间下的授权摘要并完成安全的任务、评论和审批操作。
6. 所有关键修改具备操作人、时间、来源客户端、变更对象和结果审计。
7. 保持 ForgeMind 无云服务时仍能进行基础编辑、确定性仿真和 JSON 导入导出。

### 4.2 明确非目标

- ForgeCloud 不重写 ForgeMind 的三维编辑器、碰撞、寻路和确定性仿真。
- ForgeCloud 不让大语言模型直接决定坐标、库存、路线或仿真指标。
- 第一阶段不将每帧物料、车辆坐标或 WebGL 状态写入数据库。
- 第一阶段不直接向 PLC 或真实设备下发控制指令。
- 第一阶段不拆成大量微服务，也不强制引入 Kafka、Redis 或 Kubernetes。
- 第一阶段不同时建设完整 ERP、MES、WMS 和电商平台。

## 5. 总体架构

### 5.1 逻辑架构

```text
┌──────────────────────────────────────────────────────────────┐
│ 客户端                                                       │
│ ForgeMind Web/Windows | ForgeHub3D | ForgeLab | ForgeMove    │
└──────────────────────────────┬───────────────────────────────┘
                               │ HTTPS / SSE / Webhook
┌──────────────────────────────▼───────────────────────────────┐
│ ForgeCloud API                                               │
│ 身份与组织 | 项目与版本 | 资源中心 | 社区发布 | 通知与任务    │
│ Agent 审批 | 审计 | 搜索 | 配额 | 工业连接管理              │
└──────────────┬───────────────────────┬───────────────────────┘
               │                       │
┌──────────────▼─────────────┐  ┌──────▼──────────────────────┐
│ MySQL 结构化事实            │  │ 对象存储                    │
│ 用户、权限、版本、事件索引  │  │ GLB、图片、附件、资源包     │
└──────────────┬─────────────┘  └─────────────────────────────┘
               │ Outbox
┌──────────────▼───────────────────────────────────────────────┐
│ 异步任务与连接器                                             │
│ 缩略图/校验/索引 | 通知投递 | MQTT/OPC UA/HTTP/文件回放     │
└──────────────────────────────────────────────────────────────┘
```

### 5.2 实施原则

- **模块化单体优先**：继续使用当前 Spring Boot 应用，通过包和数据库领域边界拆分模块。
- **事实分层**：设计事实、运行事实、社区内容、审计事实和二进制文件分开保存。
- **离线优先**：ForgeMind 本地工作副本继续可运行；同步是增强能力，不是启动门禁。
- **版本优先**：跨产品引用必须指向不可变版本，不能只引用会被覆盖的“最新资源”。
- **先只读接入**：现场数据首期只读，任何执行动作必须经过权限、审批和外部安全系统。
- **默认最少权限**：没有明确授权的用户、客户端和连接器不获得写权限。
- **兼容迁移**：现有 `/api/auth`、`/api/factories`、`/api/resources` 和 `/api/forgelab` 在迁移期保持可用。

## 6. 后端模块划分

建议在现有 `backend/src/main/java/com/forgemind/` 下按领域逐步建立模块，不立即拆独立进程。

| 模块 | 职责 | 首期优先级 |
| --- | --- | --- |
| identity | 用户、会话、密码策略、设备会话、外部身份 | P0 |
| workspace | 企业/团队工作空间、成员、邀请、角色 | P0 |
| project | 工厂项目、成员、分支、版本、发布和归档 | P0 |
| asset | 资源注册、资源版本、文件、预览、许可和依赖 | P0 |
| collaboration | 评论、审批、活动流、关注和协作状态 | P1 |
| community | ForgeLab 内容、发布关系、互动和治理 | P1 |
| notification | 站内信、移动通知、邮件/微信适配和已读游标 | P1 |
| agent | 现有 Agent 运行、Patch、审批、回滚 | 保留并接入权限 |
| integration | 连接器、凭据引用、设备映射和同步任务 | P2 |
| runtime | AssetTwin、运行事件、低频快照和指标窗口 | P2 |
| governance | 审计、配额、授权、保留策略和导出 | P1/P2 |

模块之间通过服务接口和领域事件协作。第一阶段使用同库事务与 outbox 表，不通过进程内任意跨模块 SQL 读取来形成隐性依赖。

## 7. 核心数据模型

### 7.1 身份与工作空间

| 实体 | 关键字段 | 说明 |
| --- | --- | --- |
| `workspace` | id、name、slug、type、status、owner_user_id | 企业、团队或个人空间 |
| `workspace_member` | workspace_id、user_id、role、status | 工作空间成员关系 |
| `workspace_invitation` | workspace_id、email/username、role、token_hash、expires_at | 邀请记录 |
| `service_account` | workspace_id、name、status、scopes | 自动化和连接器身份 |
| `api_credential` | principal_id、secret_hash、scopes、expires_at | 只保存哈希，不保存明文密钥 |

个人用户注册后自动创建一个个人工作空间。现有用户拥有的工厂和私有资源迁入该个人空间，保证旧数据不丢失。

### 7.2 项目与版本

| 实体 | 关键字段 | 说明 |
| --- | --- | --- |
| `cloud_project` | id、workspace_id、type、name、visibility、status | 统一项目容器，首期 type 为 factory |
| `project_member` | project_id、user_id、role | 项目级权限覆盖 |
| `project_branch` | id、project_id、name、head_version_id、protected | 分支指针 |
| `project_version` | id、project_id、branch_id、parent_id、schema_version、content_hash、created_by | 不可变版本 |
| `project_release` | id、project_id、version_id、release_name、notes、status | 对外或企业内发布 |
| `project_lock` | project_id、branch_id、holder、expires_at | 可选短时编辑租约，不替代乐观并发 |

`project_version` 保存经过 schema 校验的完整工厂载荷或其对象存储引用。所有更新必须携带 `baseVersionId` 或 `If-Match`，服务端发现基线不一致时返回冲突，不静默覆盖其他人的修改。

## 8. 权限模型

### 8.1 两级角色

工作空间角色：

- `owner`：空间所有权、成员、配额、删除和安全设置。
- `admin`：成员、项目、资源和连接器管理，不可转移所有权。
- `member`：创建和参与授权项目。
- `guest`：仅访问被明确共享的项目或资源。

项目角色：

- `manager`：项目设置、成员、分支和发布。
- `editor`：编辑工厂、提交版本、创建资源引用。
- `operator`：查看运行数据、处理任务和异常，不修改设计。
- `approver`：审批 Agent Patch、发布和受控操作。
- `viewer`：只读查看。

### 8.2 权限检查原则

1. 每个受保护请求先确定用户或服务账号，再确定工作空间和目标资源。
2. 工作空间角色给出最大权限边界，项目角色进一步收敛。
3. 资源可见性分为 `private`、`workspace`、`unlisted`、`public`。
4. Agent Patch 的生成、审批、应用和回滚使用不同权限，审批人与申请人可按企业策略要求分离。
5. 现场连接器凭据只允许服务端使用，永不返回浏览器或小程序。
6. 所有权限拒绝都写安全审计，但不得泄露目标对象是否存在。

| 权限 | manager | editor | operator | approver | viewer |

## 9. 项目版本与同步机制

### 9.1 工作副本与正式版本

- ForgeMind 浏览器/桌面端继续持有可离线运行的本地工作副本。
- 自动恢复存档属于用户恢复机制，不等同于正式项目版本。
- 用户主动保存时，以当前分支头版本作为基线创建新版本。
- 发布操作只能选择已经保存、校验通过且不可变的版本。
- ForgeMove 默认读取已发布版本或项目最新授权版本的摘要，不读取未提交草稿。

### 9.2 并发控制

更新请求携带：

```json
{
  "baseVersionId": "version-id",
  "clientMutationId": "uuid",
  "content": {}
}
```

服务端处理规则：

- `baseVersionId` 等于当前分支头：创建新版本并移动分支头。
- 基线落后但修改可自动合并：返回合并预览，由用户确认后提交。
- 存在结构冲突：返回 `409 VERSION_CONFLICT` 和双方版本 ID，不覆盖数据。
- 相同 `clientMutationId` 重试：返回原结果，保证幂等。

首期不实现复杂实时协同编辑；先实现版本提交、冲突提示、比较和人工合并。多人光标和 CRDT 可在真实协作需求出现后评估。

## 10. 资源生命周期

资源状态建议为：

```text
draft → validating → review → published → deprecated → archived
                    ↘ rejected
```

发布前必须检查：

- manifest schema 和稳定资源 ID。
- 文件类型、大小、SHA-256 和恶意内容扫描状态。
- GLB 可解析性、尺寸、包络、材质和纹理引用。
- 缩略图或预览是否存在。
- 作者、来源、许可证、署名和修改声明。
- 依赖资源是否存在且当前用户有权引用。
- 参数 schema 是否与 ForgeMind/ForgeHub3D 支持版本兼容。

公共资源的删除采用下架和归档，不物理破坏已发布项目的版本依赖。企业私有资源删除前必须检查项目引用并提供替换或保留版本选项。

## 11. ForgeLab 集成

ForgeLab 帖子可以关联不可变的项目发布或资源版本，而不是仅上传失去来源关系的附件。

建议增加：

- `publication_subject(type, id, version_id)`：关联工厂发布、资源版本或普通文章。
- `fork_source`：记录二次创作来源。
- `license_snapshot`：发布时固化许可文本和署名。
- `reproducibility_status`：记录资源包校验、依赖完整性和兼容版本。
- 举报、审核、下架和申诉记录。

下载工厂或资源时，服务端生成 manifest，包含版本、依赖、校验和、许可证和兼容性信息。ForgeMind/ForgeHub3D 导入后先验证，再进入用户工作空间草稿区。

## 12. ForgeMove 集成

ForgeMove 使用专门的移动摘要 API，不下载完整三维工厂存档作为常规监控数据。

移动端首期允许：

- 查看授权工作空间、项目和工厂摘要。
- 查看设备、库存、工单、异常和运行信号。
- 创建/更新移动任务，确认异常，发表评论。
- 查看并处理允许移动审批的 Agent Patch 摘要。
- 接收通知并同步已读状态。
- 网络中断时保存带 `clientMutationId` 的离线操作队列。

移动端禁止：

- 直接修改三维坐标、碰撞结论、寻路或仿真结果。
- 获取连接器明文凭据。
- 绕过项目版本和审批直接应用 Patch。
- 将离线演示数据标记为云端或现场事实。

### 13.3 请求与错误规范

所有响应携带 `X-Request-Id`。统一错误体：

```json
{
  "error": {
    "code": "VERSION_CONFLICT",
    "message": "项目基线版本已变化",
    "requestId": "request-id",
    "details": {
      "expectedVersionId": "...",
      "currentVersionId": "..."
    }
  }

```

写请求支持 `Idempotency-Key`；分页使用游标而不是无限增长的页码；列表默认限制条数；下载大文件使用短期签名 URL；所有时间统一使用 UTC ISO 8601，前端按用户时区展示。

## 14. 事件与异步任务

第一阶段采用 MySQL outbox，业务事务与事件记录同库提交。后台任务按状态抢占并可重试，避免“数据库已更新但通知未发送”的不一致。

首期事件示例：

- `workspace.member_added`
- `project.version_created`
- `project.release_published`
- `asset.version_published`
- `asset.validation_failed`
- `community.post_published`
- `agent.patch_awaiting_approval`
- `agent.patch_applied`
- `runtime.alert_raised`
- `task.assigned`

事件必须包含事件 ID、工作空间、主体、对象、发生时间、schema 版本和追踪 ID。消费者使用事件 ID 去重。只有当事件量、跨服务隔离或实时性证明有需要时，才把 outbox 消费迁入专用消息系统。

## 15. 文件、对象存储与搜索

### 15.1 文件策略

- MySQL 保存文件元数据、归属、校验和、扫描状态和引用关系。
- 开发和私有部署可使用本地兼容对象存储或 MinIO。
- 云部署使用 S3 兼容对象存储。
- 上传先进入隔离区，通过类型、大小、哈希和安全扫描后才能发布。
- 相同 SHA-256 的文件可去重，但权限和资源引用必须独立保存。
- 下载使用短期签名地址，私有资源每次下载重新鉴权。

现有 `imported_resource.model_blob` 在迁移期继续可读；后台迁移完成对象存储写入和哈希核验后再切换读取位置，未核验前不得删除原二进制。

### 15.2 搜索策略

首期使用 MySQL 全文/前缀索引与结构化筛选，覆盖项目、资源和 ForgeLab 内容。搜索索引只保存授权过滤需要的工作空间、可见性和状态字段。规模增长后再评估 OpenSearch 等独立服务。

## 16. 工业连接实施边界

### 16.1 首期连接器

优先顺序：

1. 仿真快照和历史 JSON/CSV 回放。
2. 通用 HTTP 拉取或 Webhook 接收。
3. MQTT 只读订阅。
4. OPC UA 只读节点订阅。
5. MES/WMS/ERP 的项目级适配器。

### 16.2 数据质量

每条现场数据必须携带：来源、外部设备 ID、数据点、时间戳、单位、质量码、原始值、转换规则版本和接收时间。重复消息按来源消息 ID 或确定性指纹去重；时间漂移、单位不符、质量码异常和超范围值进入隔离队列，不直接覆盖数字孪生事实。

### 16.3 控制边界

ForgeCloud 首期只读。未来即使增加下发，也必须满足：

- 命令白名单和参数范围。
- 独立审批和双人复核策略。
- 现场安全 PLC/控制系统拥有最终权威。
- 幂等命令 ID、超时、撤销或补偿路径。
- 完整审计和执行回执。
- Agent 只能提出建议，不能绕过审批直接控机。

## 17. 安全与合规

### 17.1 身份安全

- 密码使用强哈希算法和独立盐，禁止可逆保存。
- 会话令牌只保存哈希，支持撤销、过期和设备列表。
- 管理员、连接器和发布操作支持二次验证扩展。
- API Key 只在创建时显示一次，数据库保存哈希和权限范围。
- 服务账号不能交互式登录，默认没有用户级资源浏览权限。

### 17.2 租户隔离

- 每张租户业务表必须包含 `workspace_id` 或可可靠追溯到工作空间。
- Repository 查询必须显式携带授权上下文，禁止仅凭对象 ID 查询。
- 集成测试覆盖跨工作空间读取、修改、下载和枚举攻击。
- 对象存储 key 不作为授权凭证，下载前必须经过服务端授权或签名。

### 17.3 内容与供应链安全

- 上传文件限制扩展名、MIME、大小、数量和解压后总量。
- GLB、JSON 和压缩包必须防止路径穿越、递归压缩和超大结构。
- 公共资源保留来源、许可和修改声明，未知许可不能标记为可商用。
- ForgeLab 提供举报、审核、下架和审计记录。
- 依赖和容器镜像进入版本锁定与漏洞扫描流程。

## 18. 可观测性、备份与恢复

### 18.1 可观测性

最少记录：

- API 延迟、状态码、请求量和限流量。
- 数据库连接、慢查询和事务冲突。
- 上传、校验、预览生成和索引任务状态。
- outbox 积压、通知投递失败和连接器断线。
- 登录失败、越权拒绝和敏感操作。
- 每个请求的 request ID、用户/服务主体、工作空间和客户端来源。

日志不得记录密码、Bearer token、连接器密钥、完整私有存档或用户上传的二进制内容。

### 18.2 备份与恢复

- MySQL 每日全量备份加增量/binlog 恢复策略。
- 对象存储开启版本或保留策略，数据库与对象清单定期核对。
- 每季度执行恢复演练，而不只检查备份文件存在。
- 首期建议目标：核心元数据 RPO 不高于 24 小时、RTO 不高于 4 小时；进入企业试点前根据合同收紧。
- 删除采用软删除与延迟清理，安全/合规删除另行审批。

## 19. 部署形态

### 19.1 本地开发/单机模式

- 保持当前一键启动和离线前端能力。
- Spring Boot、MySQL 为推荐但可选；ForgeMind 基础编辑和仿真不因 ForgeCloud 不可用而失效。
- 对象存储可以使用本地开发目录或 MinIO。

### 19.2 团队私有部署

- 反向代理/TLS。
- Spring Boot 模块化单体。
- MySQL 主实例。
- MinIO/S3 兼容对象存储。

## 24. 关键验收用例

### 24.1 跨产品黄金路径

1. 用户创建团队工作空间并邀请设计师和运维人员。
2. 设计师在 ForgeHub3D 创建机器资源 v1，填写许可并发布到企业资源库。
3. ForgeMind 在工厂项目分支中引用该资源 v1，完成仿真后提交项目版本。
4. 项目经理发布工厂方案到 ForgeLab，帖子关联不可变项目版本和资源依赖。
5. 资源作者发布 v2，原项目仍固定使用 v1，并显示可升级提示。
6. ForgeMove 中的运维人员收到项目发布或异常通知，只能执行其角色允许的任务。
7. 所有创建、审批、发布、下载和任务更新都可以在审计日志中追溯。

### 24.2 工业试点路径

1. 管理员创建只读连接器并由服务端安全保存凭据引用。
2. 将 5–10 台现场设备映射到 ForgeMind 工厂对象。
3. 注入正常、重复、乱序、坏质量和断线数据。
4. ForgeCloud 只接受合法数据并生成运行摘要。
5. ForgeMind 显示仿真事实与现场事实的来源差异。
6. ForgeMove 接收异常，创建任务并回写处理状态。
7. Agent 可以基于事实提出方案，但未经审批不能修改项目或控制设备。

## 25. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 一次性重构现有后端 | 现有功能大面积回归 | 兼容 API、双写、分阶段切读 |
| ForgeHub3D 与 ForgeLab 边界不清 | 重复建设资源页面 | 前者负责制作，后者负责传播，Cloud 负责事实 |
| 多租户过滤遗漏 | 严重数据泄露 | 授权上下文、Repository 强制参数、越权测试 |
| 版本模型过度复杂 | 交付周期失控 | 首期只做提交、比较、冲突和人工合并 |
| 文件继续堆在 MySQL | 备份膨胀、下载压力 | 元数据与对象存储分离、渐进迁移 |
| 过早微服务化 | 运维成本高于业务价值 | 模块化单体和 outbox 优先 |
| 现场数据质量不稳定 | 错误诊断和误报 | 质量码、单位、隔离队列、来源标记 |
| 移动端权限过大 | 误操作风险 | 移动摘要、最少权限、重要操作回到工作台 |
| 公共资源许可不清 | 商业和开源风险 | 发布门禁、许可快照、来源与下架机制 |

## 26. 成功指标

首个可交付版本不以页面数量衡量，而以以下闭环衡量：

- 四个产品使用同一账号、工作空间和资源身份。
- 100% 关键写操作具有工作空间归属和审计记录。
- 跨租户自动化用例零越权。
- 项目和资源版本可追溯，已发布引用零漂移。
- 跨产品黄金路径可在一个测试工作空间内完整走通。
- 云端不可用不破坏 ForgeMind 的基础离线设计和确定性仿真。
- 首条现场试点连接在断线和脏数据下仍保持来源可识别、事实不污染。

## 28. 开工前必须确认的决策

在进入代码实施前，需要在权威方案中最终确认：

## 29. ForgeCloud 界面设计规范

### 29.1 设计定位

ForgeCloud 的界面定位为“工业控制平面 × 版本账本”。它不是新的三维编辑器，也不是由 KPI 卡片堆叠而成的通用企业后台。界面必须帮助用户快速回答三个问题：

1. 当前工作空间及其生态服务是否正常。
2. 项目、资源、发布和现场连接最近发生了什么变化。
3. 哪些审批、冲突、许可、任务或异常需要当前用户处理。

主要用户包括企业所有者、项目经理、设计工程师、运维人员、审批人员和只读访客。不同角色进入同一信息架构，但默认首页内容、主要操作和可见数据必须由权限决定。ForgeCloud 控制台内部不重复承担产品门户职责：ForgeMind、ForgeHub3D、ForgeLab 和 ForgeMove 的产品入口由门户或各自授权链路负责，云控制台专注于共享事实和服务状态。

### 29.2 视觉方向

ForgeCloud 位于 ForgeMind 深色工业工作台和 ForgeLab 轻量门户之间，使用冷静、精密、可审计的云控制台风格。大胆的视觉表达集中在首页“当前工厂与云端资源状态”主板，其他页面保持克制，避免装饰干扰工程判断。

#### 色彩令牌

| 令牌 | 建议值 | 用途 |
| --- | --- | --- |
| `cloud-surface` | `#F3F6F7` | 全局冷瓷白背景 |
| `cloud-panel` | `#FFFFFF` | 主内容面板 |
| `cloud-ink` | `#111417` | 主文字、导航和关键边界 |
| `cloud-muted` | `#687178` | 次级说明与辅助标签 |
| `cloud-grid` | `#D8DEE2` | 网格、分隔线和非活动边框 |
| `cloud-forge` | `#6547E8` | 品牌、当前选择和主要操作 |
| `cloud-signal` | `#18A999` | 正常运行、同步完成和健康状态 |
| `cloud-warning` | `#F2A93B` | 待处理、风险和注意事项 |
| `cloud-danger` | `#D74F4F` | 故障、拒绝和破坏性操作 |

状态不能只依靠颜色表达，必须同时提供图标、文字或形状。品牌紫不能用作普通装饰性大面积渐变，避免和“已选择/主要操作”的语义混淆。

#### 字体与排版

- 品牌标题和少量页面识别文字使用 `Doto`，不用于长正文。
- 中文正文优先使用思源黑体、系统中文无衬线字体栈。
- 版本号、资源 ID、时间、哈希、指标和连接数据使用 `IBM Plex Mono` 或系统等宽字体。
- 淘宝买菜体等展示字体只允许用于门户式品牌短语，不进入管理、权限、审批和审计正文。
- 页面标题、对象名称、状态、说明和技术标识建立明确层级，技术 ID 不得抢占业务名称的视觉优先级。

#### 形状与材质

- 主面板使用细边框、低圆角或直角，不使用大面积玻璃拟态。
- 列表、表格和版本轨道使用真实结构分隔，不用阴影代替信息层级。
- 三维资源和项目使用真实缩略图；无预览时使用明确的类型占位，不使用泛化 AI 插画。
- 大面积背景不使用持续运动粒子、无来源网格动画或与业务无关的光晕。

### 29.3 全局框架与导航

#### 29.3.1 ForgePass 统一身份入口

进入 `/forgehub`、`/forgecloud` 或 `/forgelab` 必须先完成 ForgePass 身份认证。登录页是三个产品共用的身份入口，不区分产品、不创建独立的 ForgeLab 身份，也不复用 ForgeMind 三维电梯舱的视觉流程，但复用同一套 `/api/auth/login`、`/api/auth/register`、`/api/auth/me` 会话协议和 Bearer token。

- 无本地会话时只渲染登录/注册页，不加载 workspace、项目、数据库状态、演示数据或控制台导航。
- 已有 token 时先由现有 `restoreSession` 调用 `/api/auth/me` 校验；校验失败清除会话并回到登录页。
- 登录成功后才挂载目标产品页面；ForgeCloud 随后请求当前用户可访问的 workspace 和数据库观测接口，ForgeHub/ForgeLab 随后进入各自业务页面。
- ForgePass 页面使用提供的 `src/components/ui/auth-fuse.tsx` 原组件，宿主适配器只负责接入现有认证 API、统一账户成功回调和入口返回，不改动原组件。
- 登录页必须提供用户名、密码、登录/注册切换、提交中状态、失败原因、返回 ForgeMind 入口，以及键盘焦点和减少动效支持。
- 数据库不可达属于“已认证但服务降级”，只能在登录后的控制台内显示 `DATABASE DEGRADED` 或 `DEMO DATA / LOCAL SHELL`，不能用它替代未登录状态。

全局导航要求：

- 工作空间选择器始终可见，并明确区分个人、团队和企业空间。
- ForgeCloud 左侧不重复显示产品启动器；跨产品跳转只在具体对象详情或门户授权入口出现，不能把尚未部署或无权访问的产品伪装成已可用入口。
- 主导航按用户认识的对象命名，不暴露后端模块名。
- 顶部搜索覆盖当前用户有权访问的项目、资源、成员和社区发布。
- 页面标题区域同时承载业务名称、状态、版本和唯一主要操作，避免多个同权重按钮。
- 当前工作空间、项目和分支上下文必须在执行保存、发布、审批等动作前保持可见。

### 29.4 首页：存档与云服务中枢

首页不再使用独立的产品启动器或“生态信号轨”，而以当前存档和云端服务状态为主语：

```text
当前工厂与云端资源状态                           LIVE
────────────────────────────────────────────────────────
当前云端存档：WZH 三层轻量完整产线 / main / v18
对象 39 · 生产设备 09 · 传送线 18 · 楼层 03
1F 供料层 · 2F 加工层 · 3F 装配层

配方产物                         Cloud API Pulse
机加工壳体 ×1                    ForgeCloud API       正常
电机总成 ×1                      MySQL                正常
已检电机 ×1                      对象存储             未接入
                                 工业连接器           未配置
```

首页由以下区域组成：

1. **当前工厂与云端资源状态主板**：展示当前工作空间最近更新的工厂项目版本、分支、schema、对象数量、生产设备、传送线、楼层及楼层名称；这是页面的主事实来源。
2. **配方产物账本**：按存档中的启用配方输出聚合物品和数量，并同时显示物品 ID、关联配方数；必须标注“按配方定义”，不冒充实时产量。
3. **Cloud API Pulse**：展示总览接口返回的 API、数据库、对象存储和工业连接健康状态；已接入和未接入必须分别表达，不能将兼容模式写成生产可用。
4. **数据库运行状态板**：单独显示已鉴权服务端的 MySQL 连通性、版本、schema、Flyway 迁移、业务表数量、占用空间、连接使用量和探针延迟；权限不足时显示降级原因，严禁以演示数值覆盖真实状态。
5. **中枢资源索引**：链接到项目、共享资源、成员和任务，并显示当前工作空间的真实计数。
6. **需要处理、最近活动、当前存档快捷入口**：继续承载审批、审计和回到 ForgeMind 的工作路径，但数据优先来自 API。

主板中的存档摘要必须来自当前工作空间可访问的最新工厂项目版本。未登录或 API 不可用时可以展示受控演示存档，但必须显示 `OFFLINE PREVIEW / DEMO DATA`，不能让演示数值看起来像用户的真实存档。对象存储或工业协议尚未接入时显示“未接入/未配置”，不能使用伪造延迟、容量或心跳。

### 29.5 项目中心

项目列表中的每个项目至少显示：

- 真实工厂缩略图或经过验证的封面。
- 项目名称、工作空间、当前分支和版本。
- 最近修改者和修改时间。
- 使用资源数量与待升级资源数量。
- 仿真/结构验证状态。
- 数据来源：仿真、历史回放或现场。
- 版本冲突、待审批和连接异常数量。

项目详情标签建议为：

```text
项目概览｜版本与分支｜资源依赖｜成员权限｜运行连接｜活动｜审计
```

版本页面使用垂直提交轨道表达真实父子关系：

```text
v18  已发布     王工              14:32
 │   调整 A-02 装配线节拍
 │
v17  已验证     ForgeMind Agent
 │   修复供料边界连接
 │
v16  已回滚     李工
     资源版本不兼容
```

默认差异视图应把 JSON 变化翻译为用户可理解的“新增设备、移动对象、调整配方、升级资源、修改成员”等变更。原始 JSON 只作为高级检查入口。

### 29.6 资源中心

资源详情页采用“真实预览 + 版本事实”结构：

```text
┌────────────────────────┬────────────────────────────┐
│                        │ CNC 加工中心               │
│      真实 3D 预览       │ asset_cnc_001 / v3         │
│                        │ 已发布 · 企业资源           │
│                        │ 许可：CC BY 4.0             │
├────────────────────────┼────────────────────────────┤
│ 参数与端口              │ 版本历史                    │
│ 依赖关系                │ 使用该资源的 12 个项目      │
│ 文件与校验              │ 来源、作者与修改声明        │
└────────────────────────┴────────────────────────────┘
```

资源页面必须使用户快速判断：资源是什么、由谁创建、许可证是否允许当前用途、当前使用哪个版本、哪些项目依赖它、升级是否会产生兼容问题。ForgeHub3D 负责编辑；ForgeCloud 负责草稿状态、验证、版本、发布、权限和依赖，不在资源页复制模型编辑工具。

### 29.7 发布、任务与审批

审批界面不能只有“同意/拒绝”。Agent Patch、资源发布和项目发布至少展示：

- 请求目标与提出原因。
- 使用的证据、来源和时间窗口。
- 修改前后结构化差异。
- 受影响的项目、设备、资源和成员。
- 确定性验证或仿真结果。
- 风险等级、权限要求和回滚能力。
- 申请人、审批人和完整审批链。

动作命名保持前后一致：

- `批准并应用`
- `拒绝`
- `要求重新规划`
- `在 ForgeMind 中检查`
- `发布版本`
- `撤回发布`

高风险布局、碰撞、库存和现场控制相关审批默认引导至 ForgeMind 或桌面端完成完整检查。ForgeMove 只承载被策略允许的摘要审批。

### 29.8 工业连接页面

连接页面使用“信号接线台”而不是三维工厂画布：

```text
现场设备        连接器          数据映射          ForgeMind 对象
PLC-A01 ───→ OPC UA-01 ───→ spindle.speed ───→ CNC-01
                         ├→ machine.state ───→ CNC-01
                         └→ energy.kw ───────→ CNC-01
```

每条映射必须显示在线状态、最后数据时间、质量码、单位与转换、隔离消息、重试状态和事实来源。三维对象通过“在 ForgeMind 中定位”打开，不在 ForgeCloud 重建三维编辑器。

连接凭据只显示“已配置/需要更新”等状态，不回显密钥。断线、错误单位、时间漂移和坏质量数据必须给出具体修复动作，不能只显示“连接失败”。

### 29.9 成员、权限与审计页面

成员页按工作空间角色和项目角色分层展示，明确权限来自工作空间、项目直接授权还是临时邀请。危险权限变化需要二次确认，并在确认内容中写明受影响范围。

审计页采用不可变事件表和详情抽屉，支持按主体、对象、动作、结果、产品来源和时间过滤。普通用户看到与自己有权对象相关的活动；企业管理员可以导出授权范围内的安全审计。技术字段放在详情区域，列表优先展示“谁在什么产品中对哪个对象做了什么以及结果如何”。

### 29.10 响应式与移动边界

- 桌面端以 1440px 为主要设计基准，并支持 1280px 常见企业设备。
- 低于 1024px 时左侧导航收为图标栏或抽屉，页面标题和主要操作仍保持可见。
- 表格在窄屏下转为分组记录，不通过无限横向滚动隐藏关键操作。
- 手机上 ForgeCloud Web 只提供审批、通知、任务和摘要的应急访问；完整移动体验由 ForgeMove 承担。
- 资源三维预览在低性能设备上提供静态封面降级。

### 29.11 动效与反馈

- 存档同步成功时只执行一次短距离状态切换反馈，不长期循环；主板不得使用持续滚动、自动计数或伪造实时波形。
- 连接恢复时从断点状态平滑过渡为正常状态，并保留恢复时间。
- 版本发布时节点由草稿空心态转换为已发布实心态。
- Morphicons 可用于导航、同步、审批和完成状态，但不得改变业务事实。
- 加载超过 400ms 才显示进度反馈；长任务展示阶段、取消入口和失败原因。
- 必须遵循系统减少动效设置，关闭非必要位移与脉冲。

### 29.12 文案规则

- 使用用户认识的业务名称，例如“管理通知”，不显示“配置 notification service”。
- 按钮使用明确动作，例如“保存草稿”“发布版本”“批准并应用”。
- 成功反馈复用同一动词，例如按钮“发布版本”对应“版本已发布”。
- 错误说明发生了什么、哪些数据未改变以及如何恢复。
- 空状态提供下一步行动，例如“还没有资源版本。前往 ForgeHub3D 创建资源”。
- 仿真、历史回放和现场数据始终标记来源，不能用“实时”混称三类事实。

### 29.13 可访问性

- 所有交互支持键盘操作和可见焦点。
- 正文与背景、状态文字与状态底色满足可读对比度。
- 图标按钮具有可访问名称，图表提供文本摘要。
- 状态不只依赖颜色；存档主板、产物账本和 API 健康列表提供顺序化屏幕阅读内容。
- 弹窗打开后管理焦点，关闭后回到触发控件。
- 危险操作不能仅靠颜色或按钮位置与普通操作区分。

### 29.14 界面验收门禁

ForgeCloud 首版界面至少通过以下验收：

1. 用户始终知道当前工作空间、项目、分支和版本。
2. 首页当前存档主板能追溯到当前工作空间的项目版本和保存载荷；配方产物能追溯到 `recipes.outputs`。
